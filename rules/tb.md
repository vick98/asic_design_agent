# Testbench

`tb_build` 的工作规则：按测试要点生成框架式 TB。被测 RTL 功能只读不改；TB 代码不做 lint。

## 组件与职责

组件分成接口（interface）、驱动（driver）、监视（monitor）、参考模型（refm）、记分板（scoreboard）、环境（env）、用例（tc）与仿真顶层（sim_top）。

- interface：与 DUT 端口一一对应，沿用 `i_`/`o_` 前缀；输入信号声明赋初值，不得为 X
- driver：取激励驱动 DUT 输入，并把已驱动激励广播给参考模型
- monitor：采样 DUT 输出，送记分板
- refm：按无状态纯函数计算期望值；模型计算与调度分开，函数内不做时序等待
- scoreboard：期望与实际双通道比对，统一计数与汇总；容差比对见 §5
- env：组件容器与连接
- tc：用例主体，按规格书测试要点编写激励；固定流程 build → connect → run → body → 等待排空 → 汇总，顺序不可改
- sim_top：DUT 例化、时钟复位接口、用例选择、全局超时、虚拟接口结构布线

## 命名

| 对象 | 格式 |
|------|------|
| 接口文件 | `<dut>_if.sv` |
| 顶层文件 | `<dut>_sim_top.sv` |
| TB 包 | `<dut>_tb_pkg.sv` |
| 组件文件 | `<dut>_tb_<comp>.svh`（comp：cfg/item/driver/monitor/refm/scoreboard/env） |
| 用例文件 | `tc/<dut>_tc_<name>.sv` |
| 用例基类 | `tc/<dut>_tc_base.sv`，类 `<dut>_tc_base` |
| 聚合用例 | `tc/<dut>_tc_all.sv` |
| 工厂注册 | `tc/<dut>_tc_factory.svh` |
| 编译清单 | `<dut|sys>_tb.f` |
| 覆盖率骨架 | `<dut>_tb_cov.svh` |
| 用例类 | `<dut>_tc_<name>` |
| 组件类 | `<dut>_<comp>` |
| 类成员 | `m_` 前缀 |
| 实例名 | `mo_<name>` |
| 宏守卫 | `U_<DUT>_TB_<COMP>`（DUT 大写） |

用例组织一测试点一用例：每条测试要点对应一个用例文件，注册在 factory，聚合进 `tc_all`；`ifdef` 包住的用例在说明里单独标出。

`python3 script/framework.py tb-gen <sys> --dut <dut>` 按上表生成全套骨架（组件、包、`sim_top`、`tc_base`、用例、factory、`tc_all`、`.f`）。用例按模块规格书第 9 节的测试要点逐条生成，命名为 `<dut>_tc_tp<N>.sv`（N 是测试要点次序），每条要点一个用例；规格书里没有测试要点时才生成一个 `tc_basic`。骨架的用例在填写前记一次失败，参考模型只做透传，都要按规格书改写后才能准出。已存在的文件不覆盖。

行 9 闸门按这两条卡死，都不是提示：`T5` 逐条核对 `spec_doc/` 规格书的测试要点编号——第 N 条要有 `<dut>_tc_tp<N>.sv`，或用例文件头注释里写 `testpoint: N`，缺哪几条就报哪几条编号；`T5` 只核对存在同名 TB 平台的规格书（模块要有 `testbench/<模块>/tc`；只有顶层 TB 时，模块测试要点由集成用例覆盖，不单独映射）；`T6` 平台任一用例文件或参考模型文件仍含骨架标记（`骨架未填写`、参考模型透传标记）即不通过。

## 时钟、复位与超时

- 时钟由接口组件内嵌生成，周期用框架宏；禁止在组件与用例里自写时钟生成
- 复位序列由 sim_top 统一编写：复位低电平保持不少于 3 个时钟周期后释放；用例经虚拟接口等待复位，禁止自造复位序列
- 全局超时由 sim_top 生成，可用运行参数覆盖；超时以失败收场，禁止自写超时块
- 结果统计只用记分板计数与汇总，禁止自造独立统计；用例不自己打印 `RESULT`。每条用例进出用 `TB_CASE_BEGIN`/`TB_CASE_END` 标记，整次仿真结束时由框架流程调用记分板汇总，打印一行 `RESULT : PASS` 或 `RESULT : FAIL`；一次比对都没有也判 FAIL。判定以汇总行为准，进程退出码不作依据
- 行 10 的全量回归按 `TB_CASE_END` 行数核对：等于 `tc_all` 枚举的用例数乘以种子数
- 重复回归换种子：种子写进运行参数（`+SEED=`），不写进用例正文

## 参数与宏

- 参数单一来源：所有可调参数只写在一份 `*_cfg.svh` 里，别处引用
- 日志用框架宏分级（错误、警告、信息、调试），禁止自研日志宏或裸 `$display` 代替分级
- 用例进出用 `TB_CASE_BEGIN`/`TB_CASE_END` 标记
- 波形分两档：平时只留结果行；要看波形时打开调试宏。波形文件由用例标记宏自动按用例切分与命名，禁止在 TB 里自行调用转储任务命名；波形格式与调试开关属于运行参数，规则不绑定具体程序
- 覆盖组以覆盖率宏隔离成骨架文件，只收集规格书点名的场景；未启用时编译行为与没有覆盖率骨架一致

## 容差比对（GOLDEN_TOL）

与算法数据或定点参考模型比对时：

- 容差用工具算出的 `GOLDEN_TOL`（`fx tol <格式>` 输出，需要参考刻度时用 `--ref`），不手写一个与格式无关的整数；容差值放 TB 包的宏或参数里
- 比对前先按规格定点位宽截取双方数据（有符号按有符号减），差值落在 `±GOLDEN_TOL` 内判 PASS，越界判 FAIL 并打印期望、实际与差值
- 控制信号（valid/ready 等）不参与容差比较，仍按精确比较
- 算法数据文件不存在时不得误报：读取前检查，失败只警告并跳过依赖用例
- 参考数据要登记生成器：`golden <sys> register --data testbench/<dut>/data/<文件> --gen <生成脚本> --inputs <输入…>` 记下产物摘要、生成脚本与输入。行 10 闸门查两件事——`testbench/**/data/**` 下被 TB 用到的数据都要登记；已登记的数据若生成脚本或输入在登记之后改过，报"需重新生成"（旧的黄金数据不得继续被当作有效期望）
