# 调试经验库（Pitfalls）

本文件积累"踩过的坑"：非显然的失败模式、绕了弯路才定位到的根因。它防的不是已修好的 bug，而是**同一类坑第二次踩**。

- **登记时机**：调试事项闭合（`item <sys> end`）前，先检索本文件——有同类坑就在原条目下补充新证据；没有同类坑则按下面四段式新登记一条。只有走完定位、拿到复算证据的才登记，猜测不算。
- **检索时机**：开新调试事项时先扫一遍对应分节；派工给子代理的排查任务，把相关条目按路径写进派工提示词。
- **条目纪律**：一条一个现象；结论必须落到可复算数据（命令、日志行、`dbg` 导出、`fx` 输出）；后来发现条目写错了就地修订并注明，不静默改。
- 本文件只登记经验，不定规则；与规则冲突时以 `rules/` 正文为准，并在条目里注明"此坑已促成规则修订：<文件>#<节>"。

## 条目四段式

```text
### P<序号> <一句话现象名>（<分节>，<登记日期>）
- **症状**：现象与一眼看上去的误判（"看起来像 A，其实是 B"）。
- **根因**：机制层面的原因，落到数据；写清"为什么症状会误导"。
- **解法**：做了什么修好的，或怎么绕开的；给出可复跑的验证命令。
- **验证**：复现命令与修好后的关键输出（运行记录号 Rxxx / fx 输出 / dbg 导出文件）。
```

## 示例（格式示范，正式条目放对应分节）

### P000 示例：PDN 阶段 OOM 的真凶是 SRAM 数量（约束与综合/时序，YYYY-MM-DD）
- **症状**：floorplan 日志在 `Inserting grid` 后立刻 `signal 9`，看起来像 PDN 网格配置问题；加 swap 只延迟被杀。
- **根因**：缓存阵列深度 4096 拆成 70+ 个 SRAM 宏，die 面积撑大 stdcell 条带图，RSS 随 die 面积涨——瓶颈在宏数量不在 PDN 配置。
- **解法**：把缓存配置改到每个阵列适配单个 SRAM 宏（深度 ≤256）；`mems.conf` 里确认 depth。
- **验证**：`mems.conf` 显示 depth ≤ 256；重跑 PDN 峰值内存从 ~14GB 降到 ~4.5GB（来源：ChipAgent `Pitfall.md` Pitfall 0，作为格式示范收录）。
