# 方法论

本框架把一个 IC 子系统从信息输入做到中端签核。主对话（主持者）负责判定、呈现、裁决登记与入库、状态落盘；写文档、写 RTL、审查按 `rules/roles/` 分工。人只做判断，机器负责证据：开发者回答"选哪个"与"这一阶段的成果认不认"，不回答"这一步走完了没有"。裁决出现即报、不攒批；协调性内容与简单决定由主持者自行处理，只有方向性裁决到开发者；所有自动流转写进事件日志与简报，不打断不等于不透明；降低验收标准的动作永不自动。

## 交互模型

人机交互只走三条通道。每个动作属于自动、决策、里程碑还是红线，见 AGENTS.md 的动作策略表（唯一事实源在 `framework/flow_model.yaml` 的 `actions:` 与 `milestones:`），规则正文只引用不重复：

- **决策（打断）**：方向或数值推不出、需要取舍时，用 `problem <sys> add --kind 待裁决 --options "A|B|C" --stop <停点> --text "<问题一句话>"` 登记候选项。**出现即报，不攒批**；协调性内容与简单决定由主持者自行处理，方向性裁决即刻报开发者，并在选项里给出"推迟决定"一项（有些决定要等前置条件达成后才能继续）。开发者点选后点选即入库，不再追问"是否确认"（`rules/decision.md`）。红线动作（方向/数值裁决的入库改写撤回、覆盖率阈值下调、带违例送审、关闭需要取舍的阻断、里程碑确认、修改动作策略表）永不自动，一律走决策或里程碑。
- **里程碑（打断）**：一个阶段的产物全部就绪时，开发者读一份审阅包回答通过与否。默认三个：M1 方案确认（行 1–3，阻塞行 4）、M2 规格冻结（行 4–6，阻塞行 7）、M3 签核放行（行 7–12）；M1、M2 点选确认，M3 唯一保留终端照抄确认语句。命令：`milestone <sys> show / confirm / reject`。
- **简报（不打断）**：`<sys>/<sys>_brief.md` 与 `status <sys> --brief`，自愿阅读；自动完成、入库裁决、回修、复核恢复全在事件日志与简报里，里程碑时集中过一遍。

另有升级上报：调试不收敛（同一事项 ≥ 5 轮）、证据异常（`state verify` 失败、来源不明的写入）、外部资源不可达、规则自相矛盾——不是决策，但按打断处理。

停点流转（哪一行自动完成、哪一行由里程碑收口、审查要求与所属里程碑）见停点总表：`AGENTS.md` 开头（规则侧同表在 `rules/steps.md` 开头），由 `python3 script/framework.py hosts` 从 `framework/flow_model.yaml` 生成。开发者审阅集中到里程碑，不逐停点问。

停点总表（行、名字、角色、闸门、完成方式、审查要求、所属里程碑）不在本文复述；每个停点写什么、审什么见 `rules/steps.md`。

## 过程规矩

- 与开发者交流时用停点名字，不只报编号：首次提到写"行 2（处理流程梳理）"，之后直接用名字；编号只留在命令、状态字段与文件名里。
- **每个工作包后跑 tick**：`python3 script/framework.py tick <sys>` 自动完成满足判据的停点、对被级联停点尝试复核恢复，并输出两张清单——"智能体下一步可做的工作"与"等待开发者的事项"。主持者按输出行动：清单上能做的继续做，等待开发者的事项即刻报（不攒批）。
- 每个停点写什么、审什么，见 `rules/steps.md`；各停点的章节模板见 `rules/templates/`，章节名以 `framework/templates/chapters.yaml` 为准。
- 控制文档只记进度和裁决。方案和规格书只写设计本身，正文从第 2 节起，口径见 `rules/documents.md`。
- 裁决两步见 `rules/decision.md`：登记待裁决问题（`problem add --kind 待裁决 --options …`）→ 开发者点选即入库（`decision commit --from --pick`）。方向性选择和数值必须由开发者点选；调试与综合优化里、停在逻辑块及以下的点选记在事项上（`rules/debug.md`），不入库，升到模块结构或方案时才入库。
- 算得出的位宽由 `script/framework.py fx` 计算。算不出的列为待裁决，不编数字。出现即报、不攒批，裁完再改；选项里给出"推迟决定"一项。
- 审查角色只出发现和建议。主持细则分两份：设计阶段 `rules/host/design.md`（行 1–6），编码与验证阶段 `rules/host/code.md`（行 7–12）。
- 上游变更只在本子系统内重推。编码输入是模块规格书；端口位宽以工具输出为准。

## 派工与并行

团队工作模式与规则（角色分工、回报时机、裁决升级路径、规模纪律）见 `rules/team.md`；本节只写并行编排。鼓励把能独立完成的执行与走查派给子代理并行做（写作角色与审查卡见 `rules/roles/`，其中行 9 的 TB 审查卡是 `rules/review/tb.md`），主持者只做判定、呈现、裁决与落盘。编排守六条，避免两个子代理改同一处：

- **先划文件归属。** 派发前写明每个子代理独占哪些文件或目录，同一文件同一时间只有一个写入者。要改别人负责的文件时先停下报告，不并行改；改完回到原负责人的范围复核。归属说不清或范围重叠的，拆开做或串行做。
- **公共文件串行。** `state.json`、`events.jsonl` 与渲染物（`*_status.md`、`*_decision.md`、`*_brief.md`）只由主持者经命令写入，子代理不直接改；控制信息的**读取**同样走命令（`decision list`/`similar`、`problem list`、`status --json`、`events`），不以取信息为目的打开这些文件；`AGENTS.md`、`skills/**`、`rules/steps.md`、`rules/pubip.md` 是 `hosts` 的生成物，只改源（`framework/hosts/`、`pub_code/`）再整体重新生成；`toolchain/active` 与剖面里的工具配置一次只由一个人改。
- **走查与生产分离。** 复核、走查派给没有参与该产物写作的子代理。审查卡是只读的（工具只有 `Read` 与 `Bash`），可以任意并行，它们不改文件。
- **作者与审查者必须不同。** 派工时由主持者登记每个工作包的作者与审查者派工号，审查记录写明两者（`review <sys> record --stop <停点号> --author <派工号> --reviewer <派工号> --report report/<文件>.md`）。框架只能校验两者不同，无法核实身份——这一局限是约定，靠事件日志回查派工与里程碑抽查兜底（里程碑审阅包抽一份审查报告原文核对）。
- **审查报告由主持者落盘。** 审查者按报告五列表原样返回；主持者把返回**原样**写进 `<sys>/report/<文件>.md`，文件头记审查者派工号，不得改动发现表。`review record --report` 登记的就是这份原文，报告时间戳因此是这一版产物的审出时间。审查角色保持只读（`Read`、`Bash`），不给自己加写权限。
- **增量复审的最小范围。** 审查发现分级处置：**阻断级**必须修复后做完整复审（可换审查者重审受影响产物）；**建议级**由作者修复、主持者逐条核对修复处（主持者未参与该产物写作时可直接核对），复审范围限定为增量——只核对修复项与其直接影响面，不重跑全量审查，并允许主持者把核对结论并审查者原报告一并落盘。重录审查记录按修复后产物指纹进行；这条是修复-复审收敛的明文口径，防止"每条建议都全量重审"把轮次滚大。
- **禁止脚本改文件。** 一切写入只用宿主的文件工具（`read`/`edit`/`write`）：它们带版本守卫（`FS_STALE_VERSION`）与逐文件的可见性。**不得**用 `sed`/`awk`/`python`/`perl` 等脚本、`cat`/`tee` 重定向或 shell 变量拼接去改写文档、规格、RTL、规则与 `state.json`——**子代理尤其**：拿脚本替代 `edit` 去改**已存在**的文件，就没有版本守卫、不能 rebase 到新版本，也不留逐文件的写入记载，出半截文件时无法定位是谁在哪一步改的（本轮有四个批次各犯过一次）；要批量改多处就逐文件用 `edit`，只有**生成全新文件**时才用脚本。脚本只允许**生成全新的派生物**（如旋转因子表 `.svh`、比对数据包），且生成器与产物一起登记、产物头部标「生成物，请勿手改」并写重生成命令。理由：脚本写入绕过版本守卫、可越出写域、失败时留下半截文件——2026-10 的一轮子系统实跑里，脚本式写入覆盖过一个模块 RTL 文件，非原子的脚本写还把 `state.json` 截断成 857 字节。主持者发现脚本式改写按阻断处理：先停写、报开发者、核对产物指纹后再继续。

派发时把上下文写全——子代理看不到主对话：任务路径、停点号、要改或要看的文件范围、必读规则（角色的 `must_read`）、依赖的裁决号与真机结论、验收条目。有依赖的步骤串行，不并进同一批。

派工提示词模板：

```text
你在 <仓库根> 执行 <任务或计划路径> 中的 <条目编号>。
先读 <该任务的必读规则>。
本轮相关的裁决：<D 号=结论>；已确认的真机结论：<V 号=结论>。
你独占的文件或目录：<列表>；这些文件同一时间只有你一个写入者。
需要改列表之外的文件时先停下报告，不要自己改。
预判清单：<开工前就能预见的取舍点逐条给出主持者已定的答案（如复位同步器归属、
端口命名优先级、参数断言形式），能答的先答掉，减少开工后的请示往返；
答不了的明确写"未覆盖，遇此停下上报"。
验收条目：<逐条列出，含命令与判据>。
回报格式：只回报结论与证据号（运行记录 R 号、参考数据 G 号、裁决 D 号、报告路径、file:line 锚点），
不回报数字结论——数字一律由主持者用闸门、fx 复算与 run 记录核对，自报数字不作验收依据。
完成后按 <回报格式> 返回；遇到计划未覆盖的方向性选择时停下询问，不要自选。
```

子代理返回后，主持者按验收条目逐项核对再落盘，不采信自报数字；核对用闸门、`fx` 复算与 `run` 记录。任何"通过"必须来自 `run` 的返回码与工具日志，子代理对结果的叙述只是转述：转述与运行记录不一致时，以记录为准并把不一致作为问题登记。

**包的大小。** 重模块（结构复杂或牵涉公共单元接口）单独成包；每个包带一条可复跑的验收命令。一个包背几份文件，以归属能不能划清为准，不设固定条数——`rules/steps.md` 里"模块规格书每批 8 到 10 份"说的是分批时携带共用口径，不是提示词里的文件数。提示词只写输入、归属、依赖的裁决、验收条目与回报格式，要读的规则给路径，不复述规则正文。

**中断与降级。** 子代理中断时不要替它猜结论：同一个派工包可以原样重派一次，再次失败就停止重派。之后由没有参与该产物写作的主持者自查，主持者若已经改过这份文件就不再担任这次走查。降级要留痕：`summary add` 写进小结、`handoff set` 写进恢复入口，交给开发者前声明"本轮无独立走查报告"。这是例外路径，不与独立走查等价，也不因为降级省掉验收条目的逐项核对。

设计阶段和编码到中端都在本框架内。装了哪套仿真器、综合器，写在 `toolchain/profiles/`，不写在本文件。
