# 调试

`rtl_sim` 的调试规则。仿真失败时按本文顺序定位，先把结论落到文档，再决定改哪一边（TB、RTL 还是规格）。调试顺序固定："先日志、再复现、再波形"。

## 先看日志

0. 运行记录自带结构化诊断（`diagnostics` 字段：compile 段的 `file:line` 工具错与 run 段的 `TB_ERROR`，见运行记录 R 号）：`status`/闸门失败信息已引用首条，先看首条诊断定位文件与行，再翻日志原文，不要一上来就全文搜。
1. 看记分板汇总行 `RESULT : FAIL`，再看日志里第一条 `TB_ERROR`：它带着用例名与比对点
2. 日志已经指出用例名和比较点时，不要先打开波形
3. `RESULT : FAIL` 但一条 `TB_ERROR` 都没有，说明卡在流程或超时：看 `TB_CASE_BEGIN`/`TB_CASE_END` 是否配对、有没有超时宏、有没有 `SEED_CRASH`
4. 逐 seed 对比：换 seed 才失败的是激励覆盖问题，固定 seed 必失败的是设计或参考模型问题

判定只认记分板汇总行，进程退出码不作通过依据；一次比对都没有也判 FAIL。

## 先复现

- 记下能复现的最小命令：场景、模块、用例、seed。运行参数由 `python3 script/framework.py run` 承载，命令原样贴进问题或小结
- 复现不了的结论不算结论：先找稳定复现条件，或明确写成"偶发，未定位"
- 缩小范围从 `--tc <用例>` 单用例开始，再回到全量回归；单用例都失败时按顺序干扰或跨 seed 状态污染查
- `tb-gen` 生成的骨架用例带 `骨架未填写` 的 `TB_ERROR`，看到它是用例还没填，不是设计缺陷

## 波形与设计查询

进入波形一步时默认走 `dbg` 系列（EDA MCP 的统一封装，任何宿主都能用；波形渲染规则见 `rules/waveform.md`）。一套调试会话先 `dbg <sys> ctx set --case N -s <信号>... --clock <时钟>` 定下默认用例/信号/时钟/窗口，后续命令缺参自动继承（输出 `fp` 的 `from_ctx` 里声明继承项；`--ctx-rev` 可钉住版本，默认值被改动即报 `ctx_conflict` 而不是悄悄换口径）。步骤：

1. **看节拍**：`dbg <sys> wave --case N -s <信号>... -t 0ns -c 16` 生成 WaveDrom JSON（落 `<sys>/work/dbg/`），对照模块规格书里的接口节拍。看波形的顺序：时钟与复位是否如期 → 握手（valid/ready）是否按规格书节拍 → 数据是不是第一拍就错。
2. **查驱动**：信号值不对时，先 `dbg <sys> npi trace <信号全路径>` 看 elaboration 后的真实驱动与负载，再读 RTL；不靠读源码猜连接。要把驱动链和**真实波形值**一起看时用 `dbg <sys> trace --case N -s <FSDB全路径> --time <T>`（沿驱动链反向遍历，每节点带该时刻值与连续赋值语句语境；`--x` 只走 x/z 分支找 X 根因）。答"某一拍是哪条驱动在起作用"用 `dbg <sys> active --case N -s <信号> --time <T> --clock <时钟>`——寄存器在沿上采集，驱动值取采集沿的**沿前一时刻**（同一时间戳上组合更新与 NBA 采集并存）；回复里 `capture_note` 会说明口径，分类是 match/differ/undecidable，不是定论。
3. **条件时间窗**：不拉全量数据自己算，把问题下推给数据——`dbg <sys> windows --case N --expr "<布尔表达式>"` 直接返回条件成立的**区间**（如 `"top.u_dut.u_x.valid == 1 && top.u_dut.u_x.cnt > 3"`）；含 x/z 的时段单列不可决时长，**绝不计入命中**，空结果与"全程不可决"可区分。回归 pass/fail 定位用 `dbg <sys> diff --case A --case B [--clock <时钟>]`：各波形按自身起点对齐到相对时间轴，返回首分歧时刻与按分歧时间排序的信号（最早分歧者才是嫌疑人，其后的差异多半是下游传染），可再接 `trace`/`active` 做因果回溯。状态寄存器的实际转移用 `dbg <sys> fsm --case N -s <状态寄存器> --clock <时钟>`（转移表+次数+首现+采集沿上的驱动值；这是本波形的**事实**，不是覆盖率，没出现的状态可能是不可达也可能是激励缺口）。
4. **整帧比对**：用 `dbg <sys> extract --case N --clock <clk> --valid <信号> --node <节点名>=<层次路径>...` 从 FSDB 按时钟沿、经 valid 门控逐拍导出节点序列（不抽稀），与 `fx` 复算或参考模型对点。**这条取代"往 TB 里插探针"作为默认做法**——调试不改 TB，`rtl_sim` 不需要编辑权限，也不会有忘记清理的探针。
5. **证据挂事项**：导出文件用 `item <sys> set --id <M号> --text "<当前做法>" --evidence <路径或R号>` 挂到调试事项上（可重复）；结论照旧写进 `item set` 的 `--text`，`item <sys> end --id <M号>` 时证据一并进事件日志。`dbg` 系列不写 `state.json`。
6. **FSDB 两个坑**（自检方法）：编译要 `+nolibcell`，否则 DUT 子树整棵缺失且不报错；PLI 链接要 `-fno-lto`。本框架剖面已带这两项；自检：`dbg <sys> signals` 列出的 DUT 层次信号数应与同一份 VCD 的 `$var` 条数一致。

**出处指纹（`fp`）**：`dbg` 每次查询的输出都带一行 `fp:`（JSON：波形路径、运行记录 R 号、输入摘要一致性、远端波形 mtime/size、ctx 继承项）。把不同波形的答案拼进同一条推理链之前先比 `fp`——不同源的证据不许拼成一条链；引用证据时把 fp 里的 R 号一起写进事项。

只有拿不到 FSDB（比如只能跑 VCD 的场景）时才退回 §序列级节点导出（后备）的 TB 探针做法。波形是某次运行的产物：`dbg` 输出第一行会标明"波形来自 R0xx，之后 RTL/TB 已改动"，调试旧波形是正常需求，不阻断；NPI 查询则必须对得上当前 RTL。只倾倒规格书点名的层次；只有比对窗口才错的，回参考模型算一遍期望值，先确认是模型错还是设计错。

## 接口节拍

接口节拍写在模块规格书里，用 WaveDrom 描述时钟、有效与数据的相对关系；wave 字符与字段速查见 `rules/waveform.md`。节拍与规格书不符时，先确认规格书是不是漏写或写错，再动 RTL。

## 序列级节点导出（后备：拿不到 FSDB 时）

默认做法是上一节的 `dbg <sys> extract`；只有拿不到 FSDB 时才在 TB 里加临时探针把节点按拍落盘。四条口径：

1. **写法**：层次引用只读 DUT 信号，按该节点的 valid 门控后 `$fopen/$fdisplay` 落盘；不用 `$monitor` 代替落盘，也不用波形替代序列。层次路径先对规格书点名的层次核对，报 `IND`/`XMRE` 先查层次与信号存在性，再写探针。
2. **命名与位置**：`<sys>/work/dbg/<用例或包>_<节点>.txt`，节点名与行 2 节点表同名。`work/` 是工具产物，pull 回来照常用；清理对象是 TB 源码里的探针，不是这些落盘文件。
3. **归属与清理**：探针用可搜索的标记包住（`//DBG_BEGIN` … `//DBG_END`），只在调试期存在于 `testbench/` 源码里；送审所用的那次回归之前从源码删掉，归入 `rtl_sim` 交付自检的"调试打印已清除"。不把标记块做成正式 TB 结构，也不为探针建独立文件与挂载点。
4. **参考模型入口**：写在该子系统 `info_input/` 的说明里（模型、环境与解释器路径）；`toolchain/profiles/` 只放 EDA 工具，不放参考模型解释器。

观测口（`obs_sel` 与节点表）只承担关键电平抽查，整帧序列一律走 §波形与设计查询 的导出路线（拿不到 FSDB 才走本节）。

## 结论写回文档

- 调试失败不登记 `problem`：开工先 `item <sys> open --kind 调试 --side tb|rtl|spec --text "<事项一句话>"`，排查进展与修法用 `item <sys> set --id <M号> --text "<当前做法>"` 覆盖（不写根因、改法步骤与 seed），证据用 `--evidence` 挂上；`problem` 留给设计阶段的阻断与待裁决，登记口径不变
- 本轮排查过程与结论：写进小结（`summary`），不把大段日志贴进规格书
- 需要开发者点选的方向或数值：停在逻辑块及以下的记在事项上（`item set`），升到模块结构或方案才登记待裁决问题并入库（见 `rules/methodology.md`），不自行决定
- 结论涉及接口或数值的：同步回填规格书，不让规格书与 RTL 出现两个数值

## 调试回修

回修不是边改边补，顺序固定：

1. **定位**：按本文前半段拿到用例名、seed、第一条 `TB_ERROR` 与最小复现命令。
2. **证据**：把"哪一级的哪个量、在哪个点上与参考不一致"落到可复算的数据上——`dbg <sys> extract` 导出、`fx` 复算、参考模型同激励重算。没落到数据上的结论不算证据，不许据此改代码。取证据按 `rules/templates/debug_evidence.md` 的四源对照表填（规格↔RTL↔运行日志↔波形导出逐列咬合，矛盾点即根因）；L1 及以上回修定级前表格必须填完。
3. **登记**：开工先 `item <sys> open --kind 调试 --side tb|rtl|spec --text "<事项一句话>"`，不登记 `problem`；排查进展与修法写 `item set`（覆盖当前做法），本轮过程与结论写进小结。
4. **定修法**：按改了什么口径定级（L0–L3）。**L0/L1 由智能体按证据自行决定**，不打断开发者，定级与回修结果进简报；**L2/L3 是决策**（打断）：端口、参数、组成、连接、架构或方案级口径要变时，用待裁决问题提报，开发者点选后才改。
5. **迭代验证**：改一轮跑一轮，直到失败现象消失，且**不是**靠放宽期望、改软容差、删用例换来的通过。
6. **回修**：确认收敛之后，按下面四级回修文档，再重跑受影响的停点。

| 级别 | 改了什么 | 回修动作 |
|------|----------|----------|
| L0 | 只改实现写法；逻辑块的功能、关键公式、拍数、移位/舍入/饱和、复位与中间量格式都不变，端口与连接也不变 | **不回修**。逻辑块章写功能与口径，不描述代码怎么写 |
| L1 | 逻辑块功能或关键公式变了，或增删了逻辑块（拍数、移位、舍入、饱和、复位、中间量格式随之变） | 回修该模块规格书的逻辑块章与受影响的处理流程、实现结构章；`advance <sys> --stop 6 --to 进行中` 退回重推（退回用 advance，重新推进由 `tick` 做） |
| L2 | 端口、参数、组成模块、连接关系或模块架构变了 | 回修该模块规格书对应章，再上行回修子系统规格书的端口表、模块摘要与实例化契约；退回到承载该章的最早停点（接口变化退行 4，结构变化退行 5）并级联；收尾时把结构变化入库为裁决（`item <sys> end --id <M号> --level L2 --sync "<回修章>" --decision <D号>`） |
| L3 | 触及处理流程、节点定点格式或方案级取舍（子模块划分、公共单元选型、容器口径等） | 收尾时把方案变化入库为裁决（`item <sys> end --id <M号> --level L3 --sync "<回修章>" --decision <D号>`），再按裁决回修流程、方案与规格书；退回停点按裁决自己的停点（`--stop`）与依赖闭包级联 |

- 定级只看"改了什么口径"，不看改了几行：删掉一整块实现但口径不变仍是 L0，改一行公式仍是 L1。
- 与已入库裁决冲突的修复（例如实测证据表明某条裁决的换算写错了）不得静默改代码：先提报该裁决的修订或撤回，按裁决结论回修。
- 公共单元（`pub_code/`）本体改动：同步 `rules/pubip.md` 的端口与参数表，并跑它的 TB（含参数变体）留运行记录：`run sim --scenario pubip --module <ip> --sys <sys> --define <变体宏>`（默认变体不带 `--define`；日志与回拉产物落 `pub_code/work/<ip>/`，不进子系统台账）。
- 回修只改受影响章节，横向同步同链的其他规格书，不让同一个中间量出现两个数值。
- 回修会改指纹：`status` 按指纹把对应停点判过期，先 `advance <sys> --stop N --to 进行中` 退回，其后已启动的行自动级联退回（有了新证据后由 `tick` 自动复核恢复/重推）。
- `item <sys> end --id <M号>` 不代为 `advance`：退回与级联由主持者在收尾之前按现有指纹机制做完。

## 调试事项（构建—仿真回路的退回与闭合）

行 9 与行 10 是构建—仿真回路。失败时开一条调试事项并写明退回侧：`item <sys> open --kind 调试 --side tb|rtl|spec --text "..."`——`--side` 记的是退回哪一侧（TB、RTL 还是规格），决定重开哪一行。开事项前先检索 `rules/pitfalls.md` 对应分节，有同类坑按既有条目直接试解法；修好复核后 `item <sys> end --id <M号>` 即闭合，不要确认语句；闭合证据（运行记录号、导出文件、裁决号）随事项进事件日志。**闭合前检索 `rules/pitfalls.md`：有同类坑就补充新证据，没有就按其四段式登记一条**——只有拿到复算证据的才登记，猜测不算。

判据：**存在在途调试事项时，由停点总表标了"在途调试事项挡送审"的停点不得完成/送审**（范围读 `framework/flow_model.yaml` 的 `blocked_by_items:`）——这条常驻，替代旧的"回路侧未闭合不得送审"。闭合不靠退回另一行来完成——那会把已完成的停点拖成待重推。同一事项每轮 `item set` 计一轮，迭代 ≥ 5 轮未收敛按升级上报处理（`tick` 把它列入"等待开发者"）。

状态文档与简报里只显示在途事项："`<侧>`（调试中，M0xx 在途）"。`item <sys> end --id <M号>` 即闭合，事项从在途清单消失；闭合动作与随附证据落在 `events.jsonl`（"事项收尾"事件）。

## 常见错误

- 不看日志直接开波形，最后发现是参考模型写反了符号
- 只报"仿真不过"，不给用例名、seed 与第一条 `TB_ERROR`
- 把 `RESULT : FAIL` 当成工具退出码问题去查
- 只看一个 seed 就下结论
- 结论只留在对话里，既没开调试事项也没写小结
- 还没确认修复收敛就先回修规格书，或反过来改完 RTL 不回修（L1 以上）
- NPI 查到旧设计：`design_id` 带的是 RTL 摘要，代码改过要先重开设计再查

## 交付前自检

1. 每条失败都有复现命令、用例名、seed
2. 调试事项已按级别收尾（`item <sys> end --id <M号>`）；L1 以上文档已同步；L2/L3 的结构或方案变化已入库
3. 未把大段日志或波形截图贴进规格书
4. 已按 §调试回修 定级并完成回修与退回重推（L0 不回修也要能说出为什么是 L0）
5. 在途调试事项已全部 `item <sys> end --id <M号>` 闭合
