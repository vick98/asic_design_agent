# 裁决

裁决的唯一事实源是子系统的 `state.json`：只由引擎经命令写入，查询也走命令（见下「查询」）；`*_decision.md` 是引擎随事务渲染的派生物，给人读、不手改、**不是 agent 的信息来源**。效力从高到低：裁决、输入文档的强约束、权威、参考。

两步（点选发生在改产物之前，所以没有"先入队、后确认"的中间态）：

1. **登记问题**：`python3 script/framework.py problem <sys> add --kind 待裁决 --options "取甲|取乙" --stop N --text "..."`。候选写在 `--options`（`|` 分隔），停点写 `--stop`。
2. **点选即入库**：开发者在候选里点选后，`python3 script/framework.py decision <sys> commit --from I003 --pick 取乙 --kind 方向`——直接领正式号 `D<阶段>-NNN`、**自动关闭 I003**（证据就是这条裁决）、按停点级联。产物里直接写 `〔D0-001〕`，没有临时号要替换，也不再追问"是否确认"。

类别：

- **方向 / 数值**：必须有点选来源（三条，见「点选来源留痕」：`--from/--pick` 点选、mark 收割、里程碑拒绝理由自动落的问题）。入库级联重推该停点下游已完成停点。
- **记录**：`decision <sys> commit --kind 记录 --content "..." --stop N` 直接入库，不必先登记待裁决问题，由智能体按规则做；不级联。

阶段号由停点的 `stage:` 字段推导（见 `framework/flow_model.yaml` 的 `stages:`，模型是唯一事实源），D 号格式 `D<阶段>-NNN` 只增不复用；命令只认 `--stop`。

## 查询（agent 只走命令，不读渲染物）

读裁决与问题的出口都在命令里，不以读信息为目的打开 `state.json` 与 `*_decision.md`：

- 全量与过滤：`decision <sys> list [--json] [--kind 方向|数值|记录] [--stop N] [--stage S] [--grep <词|正则>] [--limit N]`。`--grep` 先做子串/正则命中，未命中的再按重合度给相近条目（标进"匹配"列）
- 单条全档：`decision <sys> list --id <D号>`——正文、来源、修订历史（override 前的旧正文）与关闭该裁决所对应的问题
- 比较正文：`decision <sys> similar --content "…"`——入库前判"是不是同一条"用这个，按重合度排名；与入库守卫同一套算法（阈值不同：similar 缺省 0.25，入库拦截 0.60）
- 待裁决与已推迟问题：`decision <sys> list --open` 或 `problem <sys> list --json`（`--all` 连已关闭一起列）
- 事件留痕：`events <sys> [--grep <词|正则>] [--limit N] [--json]`
- `--json` 的口径与 `status --json` 一致：stdout 只有一份 JSON，错误走 stderr、退出码非 0

## 推迟决定

有些决定要等前置条件达成后才能继续。呈现选项时照样给出"推迟决定"一项，但推迟**不是裁决**：不领 D 号、不关问题：

- `python3 script/framework.py problem <sys> defer --id I00x --until <停点号|M1|M2|M3> [--reason "…"]`：问题保持打开，记下解除条件与原因。
- 推迟条件满足前，`tick`/`status` 的"需要开发者"不重复列该问题；`--until` 指向的停点已启动、或里程碑已就绪/已确认后，重新列出（结构里的 `kind` 为 `deferred`，带"推迟条件已满足"），再按正常点选入库落定。
- "推迟决定"是保留词：`decision commit --pick 推迟决定`、mark 收割正文恰为"推迟决定"都会被拒，提示改用 `problem defer`。
- 覆盖范围内还有已推迟而未落定的问题（问题的 `stop` 落在里程碑 `covers` 内）时，`milestone confirm` 拒绝。

## 走查标记（mark 收割）

产物里的 `mark:` 与 `@@` 是开发者亲笔写的输入：`python3 script/framework.py marks <sys> --harvest --kind 方向 --stop N` 按原文直接入库，来源记 `mark:<文件>:<行>`。默认一次把待收割的标记全部入库；在 state 的 `thresholds.marks_cap` 配置了上限时按上限收割。同一处只算一条——已入库的标记不会重复收割；未收割完的用 `marks <sys>` 列出后继续。类别由主持者判定，被收割的条目在里程碑审阅包里高亮。

## 一个内容一条裁决

编号只增不复用，指的是**新内容**取新号；同一个内容不允许出现两条裁决。这条内容是同一对象上的同一个结论（同一帧长、同一寄存器语义、同一资源归属、同一接口来源）时，后来的结论不再另开编号。拿不准是不是同一条时，先 `decision <sys> similar --content "…"` 比对再动手：

- 修订型改动走 `decision <sys> override --id <D号> --content "..."`，在**原编号**下改写正文；旧正文进该条目的 `history`，可追溯，不丢历史。已完成的停点照旧按指纹退回重推。
- 只有确实的新内容（新对象、新接口、新资源、新流程）才取新号（方向/数值类仍要有一次新的点选来源）。
- 整条不再成立时用 `withdraw`：只标"已撤回"并保留历史（不领新号、不重新入库），撤回的裁决不再是有效证据；同一内容的两条历史遗留合并时，保留**最早那条**的编号（正文改写为最新结论），其余 `withdraw`。
- 入库与改写都会按字符三元组重合度比对已有裁决：重合度达到阈值即报错并列出候选条目，提示改用 `override`；确属新内容才用 `--force --reason` 放行，理由记进该条备注。自动判定只是拦一下要求写明理由，不做终审。
- 复核既有产物时若发现同一内容有多条裁决（规则生效前的历史遗留），按上一条口径合并，并把合并动作写进本轮小结。

## 类别守卫与记录类提示

- **方向 / 数值**：必须来自开发者点选，属红线；没有点选来源（既不是 `--from/--pick`，也不是 mark 收割，也不是里程碑拒绝理由转成的问题）**直接拒绝**，`--force` 不放行这一条。
- **记录**：不承载变更语义，由智能体直接入库与改写（`override`），进简报；但**不级联**。已完成停点的产物若在完成后被改动，跑 `tick` 会把它自动退回进行中并按依赖级联（`gate` 仍报规则号 `fingerprint`，不可豁免）。
- **记录类提示（防夹带）**：记录类入库时，正文含位宽格式 `<w,f,t>`、裸数字加单位、或模块名的，命令输出提示"疑似方向或数值类"——类别标签是入库方自填的，实质变更不得标成"记录"绕过点选；被提示的条目在里程碑审阅包里高亮，由开发者集中复核。

## 点选来源留痕

方向/数值裁决的 `source` 记下这次点选来自哪里，共三条来源：

- `I003/取乙`——开发者在待裁决问题的候选里点选；问题由 `problem <sys> add --kind 待裁决 --options "取甲|取乙" --stop N --text "<问题一句话>"` 登记。
- `mark:<文件>:<行>`——走查标记收割；标记是开发者亲笔，正文本身就是被点选的内容。
- `milestone reject <M 号>`——`milestone <sys> reject --id <M号> --reason "…"` **不直接产生裁决**：它先把拒绝理由落成一条 `kind: 待裁决` 的问题（问题的 `source` 记 `milestone reject <M 号>`，候选为空），开发者再 `decision <sys> commit --from <问题号> --pick "<结论>" --kind 方向|数值` 入库；候选为空时 `--pick` 就是结论本身。这一步点选不能省，里程碑拒绝不是绕过点选的旁路。

事件日志同时记下问题原文与所选项。里程碑 M1/M2 同样要 `--pick 通过`（来自主持者的点选工具）并记进里程碑记录；M3 保留交互终端照抄。人的判断落在点选来源上。

不要把 decision 命令包进会吞退出码的管道（如 `cmd | sed`）；确需加工输出时先 `set -o pipefail`，或分两步执行。

动作归属（自动 / 决策 / 红线）见 AGENTS.md 的动作策略表；本文只写裁决怎么做。
