# 团队工作模式与规则

本卡在开发者要求"以智能体团队模式工作"时生效；未要求团队模式时，按 `rules/methodology.md` 的单智能体口径工作。**身份是固定的、不是选出来的**：主持者就是主会话的那个 agent；成员是主持者按任务派发出去、负责某一个任务的队员。本卡讲团队模式的组织与协作；文件归属、脚本禁令等执行细则仍指 `rules/methodology.md` 的"派工与并行"，本文只写指针不重复——唯一事实源只写一处。本卡部分源自早期多智能体实跑的做法记录，有意未吸收的条目见文末"待完善"。

## 适用与范围

- **分工**：`rules/methodology.md` 的"派工与并行"写并行编排的执行细则（文件归属、公共文件串行、走查与生产分离、作者与审查者必须不同、禁止脚本改写）；本文写团队模式的组织与协作——成员怎么分、层级与职责怎么分工、怎么协调、谁把什么留在自己上下文里。
- **层级**：开发者 ↔ 主持者 ↔ 成员 ↔ subagent。越往下走的只能是**协助性工作**，不得把任务整包下传（口径见下节）。

## 成员分配方式

任务导向，一个任务一个成员：

- **任务是组织单元，角色是技能包**：角色不是常驻编制，是 `skills/` 里的技能。成员接任务时按任务装载角色技能；**不设常驻角色池**，任务完成即回收。
- **任务粒度以"可独立验收"为准**：交付物明确到文件（或文件集合），带可复跑的验收判据。
- **有依赖的任务串行**，不并进同一批。
- **框架自身的改进性任务（改引擎、规则、测试）由主持者直接完成并测试**，不转手成员。

## 层级与职责

| 层 | 职责 | 不做 |
|----|------|------|
| 主持者 | 唯一对开发者负责的接口；唯一写 `state.json` 与 `hosts` 生成物（改源 `framework/hosts/` 再整体重生成）；统一提交；派工前划写域、写明验收条目与必读锚点；在批次边界跑完整验证 | 不阻塞等待成员；不替成员改文件 |
| 成员 | 接一个任务；**尽量把该任务的实际工作派给 subagent 去做，自己负责该任务的协调与汇报**；跑定向验证；按下方"回报时机"回报 | 不写 `state.json`、`events.jsonl`、渲染物（`*_status.md`/`*_decision.md`/`*_brief.md`）与 `hosts` 生成物；控制信息只用命令查（`decision list`/`similar`、`status --json`、`events`）；不改写域外的文件 |
| subagent | 协助成员完成该任务；也可以把**协助性工作**再派给下一层，不必全都自己干 | **不得把接到的任务整体外包或整包向下传递**（任务被一层层转手，会因提示词逐层失真而出错）；不充当协调者——不划写域、不做裁决、不越级向主持者汇报 |

## 协调方式

流程四步：**派工 → 划写域 → 回报 → 裁决升级**。

1. **派工**：主持者把上下文写全——任务路径、独占写域、验收条目、必读锚点（必读规则给路径，不复述正文）。派工提示词模板见 `rules/methodology.md` 的"派工与并行"。
2. **划写域**：同一文件同一时间只有一个写入者；`state.json` 与 `hosts` 生成物只由主持者处理。归属划分、公共文件串行、禁止脚本改写的细则见 `rules/methodology.md` 的"派工与并行"，本文不复述。
3. **回报**：按下表时机。
4. **裁决升级**：成员遇到下列情况一律停下上报主持者，不自行决定；subagent 遇到则报给派出它的成员，不越级。

| 情况 | 例子 |
|------|------|
| (a) 要改自己写域外的文件 | 公共接口、别人的模块、`state.json` |
| (b) 规格/指令与代码事实冲突 | 任务描述与 RTL 现状矛盾、两个来源给出不同口径 |
| (c) 需要开发者拍板的取舍 | 方向或数值推不出、多个方案各有代价 |
| (d) 发现必须放宽既有守卫 | 需要新的 lint 抑制、闸门豁免、覆盖率阈值下调 |

需要开发者点选的，由主持者按 `rules/decision.md` 登记为待裁决，并**即刻**报开发者（不攒批）；协调性内容与简单决定由主持者自行处理，不到开发者。

### 回报时机

| 时机 | 是否回报 | 内容 |
|------|----------|------|
| 详细进展 / 中间步骤 | 不回报 | 留在成员自己的上下文与文件里 |
| **阶段性进展** | **要回报** | 一个阶段或一个可验收子步完成时，报一段简短进度：做完了什么、下一步、有无阻塞 |
| 完成 | 必报 | 交付物 + 验收证据（用例/命令、结果、耗时）；并说明"任务完成，可以释放写权限" |
| 需要裁决 | 必报 | 越界依赖、规格冲突、需要取舍、发现既有守卫会被打破 |

主持者不去催"详细进展"，但要跟踪阶段性进展。

回报只含五项，不贴长散文、不复述中间步骤：结论摘要；`file:line` 锚点；验收证据（跑了哪些用例/命令、结果与耗时）；与任务描述不符的代码事实；留给主持者的后续项。证据给指向不给数字结论：数字一律引用运行记录 R 号、`fx` 输出或报告路径，由主持者复算（`rules/methodology.md` 派工模板的回报格式条）。

## 写权限（申请与授予）

写权限台账是**协调机制，不是强制机制**——宿主的文件工具不会被脚本拦住，靠团队遵守：

- **成员不自己取锁**：成员向主持者申请；主持者按任务排期，用 `python3 script/framework.py lock grant --to <成员> --task <任务> --paths <文件或目录…>` 授予（目录以 `/` 结尾）。两名成员的路径相交时 `grant` 直接拒绝并点名持有者，主持者据此协调排队，而不是让成员互相抢。
- **排队由台账记着**：成员用 `lock request --to <自己> --task <任务> --paths <…>` 把申请记进**等待队列**（只排队、**不产生写权限**）；`lock list` 按申请先后列出队列，并标出每条是"可立即授予"还是"等 <谁>"。主持者释放后按队列顺序 `grant`；成员撤申请用 `lock cancel`。队列与已授予同在一份 `locks/registry.json`，仍只有一个文件。
- **限时**：授予带限时（缺省 30 分钟）；超时自动释放并清掉条目——要继续写须由主持者 `lock renew` 续期或重新授予；任务完成即 `lock revoke`。台账只有一份 `locks/registry.json`，不按锁分文件、不积累。
- **写前自查**：成员动手前 `lock check --to <自己> --path <路径>`，退出码 0 才算持有；`lock list` 看全盘与剩余时间。
- **子代理的写范围由成员下发任务时限定**：子代理不申请写权限；要扩范围，子代理报给成员，成员向主持者申请后由主持者扩锁。
- **释放是双重保险**：成员任务完成**要主动向主持者说明"可以释放写权限"**；主持者**不依赖这句话**——只要判断该成员的任务**已完全完成**，就**主动释放**（`lock revoke`），并把锁按排队顺序授予正在等待的成员。两道保险，防的是"成员忘记说明、锁被占住而别的成员干等"。

## 主持者需要知道的规则

主持者的身份是固定的——就是主会话的那个 agent。以下是它需要遵守的规则：

- **派工后不等待**：不得阻塞等待成员，不把回合花在轮询上——**禁止用阻塞式等待原语**（如 `wait_agent` 长超时、前台 `run wait`、sleep 轮询）等成员回报：那会挡住开发者在等待窗口内输入。成员回报以消息到达，主持者回合内只做不依赖该回报的工作；暂时无可做的工作就**结束回合**，把控制权还给开发者，回报到达时再被唤醒继续。等待期间照常响应开发者、推进其他可做的工作。自己跑长任务（全量回归、综合、STA）也用后台执行——`run … --detach` 起作业，再用 `run wait --job` 取结论，不把前台卡在墙钟上（命令口径见 `rules/sim.md` 的"长任务与后台作业"）。
- **派工前写全**：划写域、写明验收条目与必读锚点；有依赖的任务串行，不并进同一批。
- **验证在批次边界**：完整 `selftest` 只在批次边界跑，不在并发批次中途跑——避免并发抢 CPU，也避免把"别人在途改动导致的假失败"当成成员的问题。核对按验收条目逐项进行，不采信自报数字（核对手段见 `rules/methodology.md` 的"派工与并行"）。
- **跟踪阶段性进展**：成员报来的阶段进度看完记结果，不打断、不追细节。
- **唯一写者**：`state.json` 与 `hosts` 生成物只由你写（改源再整体重生成）；统一提交，使来源不明的改动可 diff、可归属、可回滚。关键写入后立即用命令复核（`status` 输出可读、`shasum` 对指纹），不一致停下。
- **写权限你一个人管**：成员申请、你授予/续期/撤销（`lock grant` / `renew` / `revoke` / `list`）。它是你的排期记录，不是自动争抢退避机制。**释放要双重保险**：成员说明可以释放时你释放；成员忘了说明、但你判断该任务**已完全完成**时，你**同样主动释放**，把它授给正在等待的成员——不让锁被占住。
- **裁决分层、出现即报**：成员遇到裁决即刻上报，不攒批。**协调性内容与简单决定由你直接处理**（写域冲突、排期、命名、顺序）；**方向性裁决**（方向、数值、冲突、回修升级、红线）**即刻报开发者**，并在选项里给出"推迟决定"一项——有些决定要等前置条件达成后才能继续。
- **高风险文件走报备协议**：改前报备（文件 + 要点 + 依据 + 写者）→ 解锁单个文件 → 改完立即重跑验证 → 复锁。
- **走查中断不替成员猜结论**：同包原样重派一次，再失败按 `rules/methodology.md` 的"中断与降级"处理。
- **并发失败先判归属**：批次并行时用例失败，先对照 `git status`、文件 mtime 与派工记录判断是不是别人在途改动造成，再决定是否上报；不得替成员改文件。

## 成员需要知道的规则

成员的身份由主持者的派工产生——按任务派发、负责某一个任务。以下是它需要遵守的规则：

- **一个任务一个成员**：接任务时按任务装载角色技能（`skills/`）；任务做完即回收。
- **尽量派 subagent 做实际工作**：你的上下文很珍贵——读写、搜索、跑验证尽量派 subagent 承担，你自己负责该任务的协调、汇总与汇报。
- **subagent 是协助者，但任务不外包**：可以把**协助性工作**再派给下一层，不必全都自己干；但**不得把你交给它的任务整体转手、整包往下传**——任务一层层转手，会因提示词逐层失真而出错。它也不当协调员：不划写域、不做裁决、不越级向主持者汇报；越界、冲突、取舍一律报给派出它的成员。
- **回报按时机**：见"回报时机"表——中间步骤留在自己的上下文与文件里；阶段性进展报简短进度；完成与需要裁决必报。
- **跑定向验证**：只跑与自己写域相关的用例/命令，写后即跑。
- **不越界**：不写 `state.json` 与 `hosts` 生成物，不改写域外的文件；越界、冲突、取舍、守卫会被打破，一律停下上报。
- **写权限先申请**：动手前 `lock check` 确认自己在写权限内，不在就停下向主持者申请（成员不自己取锁、不互相抢）。子代理的写范围由你下发任务时限定；它不申请写权限，要扩范围由你向主持者申请。
- **完成即说明释放**：任务做完，在完成回报里明确写"任务完成，可以释放写权限"，不要等主持者来问。
- **写入只用宿主文件工具**：`read`/`edit`/`write`；不得用脚本改写已存在的文件——细则见 `rules/methodology.md` 的"派工与并行"。

## 上下文经济

主持者与成员的上下文都珍贵。团队模式下"谁该把什么留在自己上下文里"：

- **原料与长文留在成员（或它的 subagent）那边**，落在文件里；向上**只报结论、`file:line` 锚点与验收证据**。
- **主持者的上下文只保留决策与结果**，不复述长文；长文落文件。
- subagent 的产物同样只以结论与锚点进入成员的上下文，成员再按"回报时机"向上收敛。

## 规模纪律

同批并行 ≤3；同时存活 ≤9（宿主硬上限）。任务完成即回收，不做常驻角色池。一个成员可连续承担多个任务，但不共享写域。

## 事故处置

写入冲突或产物被来源不明地覆盖时，按五步走：**停写 → 取证（mtime/大小/断点/并发者）→ 恢复（优先外部副本）→ 复盘 → 规则化**。教训写进规则正文，不只写进对话。

## 待完善

以下条目为早期实跑中未纳入本卡的做法，供下一轮完善：

- 任务板代替口头协调（`claim / blocked_by / complete` 作为唯一排期真值）；本卡暂用主持者的派工记录替代，未固化为模板。
- 意图广播：开工前广播"本轮要写 X、Y"，完成后报"文件 + mtime + sha256 + 行数"，写域冲突在写前暴露。
- 验证独立性分级：作者自检 → 同伴只读走查 → 第三方独立复算。
- 数字口径继承时回扫派生值：继承既有裁决后，凡由该数派生的量一起核。
- 锁要带指纹：锁定时记 `sha256`，解锁 → 写 → 复锁三步都比对指纹变化。
- 记录与产物用命令对照：小结与提交信息里的数值声明附可复核命令与输出。
- 常设支撑职务（只读 verifier / 整合者 / 改进观察者）按需唤醒的形态；本卡只保留"走查与生产分离"的指针。
- 派工包、任务卡、验收卡、事故报告卡模板固化进 `rules/templates/`。
