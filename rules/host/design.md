# 设计主持

停点 1 到 6 的主持卡。先查证再提问的规矩、各停点写什么审什么的索引、裁决与文档口径分别在
`rules/steps.md`、`rules/decision.md`、`rules/documents.md`，冲突以规则文件为准。
每个动作属于自动、决策、里程碑还是红线，见 AGENTS.md 的动作策略表；本卡只写怎么做，不复述归属。

## 恢复会话

1. `python3 script/framework.py status <sys>` 读当前位置；多子系统未指名且不止一个在途时列清单请开发者点选（消歧，见动作策略表）
2. 读恢复入口（`state["resume"]`，status 文档的"恢复入口"段）：先核对上次交接的未决项是否已结算，未结算的按该条继续，不重复产出
3. 列出未关闭的阻断问题；阻断未清不推进，先处理
4. `python3 script/framework.py marks <sys>` 扫 `mark:` 与 `@@`；收割用 `marks <sys> --harvest --kind <类别> --stop N` 按原文直接入库（标记本身就是开发者的输入，不再问"是否收割"）
5. **每个工作包后跑 tick**：`python3 script/framework.py tick <sys>`，按输出的两张清单（"智能体下一步可做的工作"/"等待开发者的事项"）行动——能做的继续做，等待开发者的事项即刻报（不攒批）。

## 停点流转

- 本卡覆盖停点 1–6。哪一行自动完成、哪一行由里程碑收口、审查要求与所属里程碑，见停点总表（`rules/steps.md` 开头，同表也在 `AGENTS.md` 开头；由 `python3 script/framework.py hosts` 从 `framework/flow_model.yaml` 生成）；本卡不复述完成方式。
- 本卡范围属 M1 方案确认与 M2 规格冻结两个里程碑（覆盖与阻塞行见停点总表）：覆盖停点就绪后进入"待里程碑"，`python3 script/framework.py milestone <sys> show --id M1|M2` 生成审阅包，开发者点选通过/不通过；`confirm` 把覆盖停点一起置完成，`reject --reason` 按依赖退回最早有问题的停点。
- 唯一保留终端照抄确认语句处在 M3（编码与验证阶段，见 `rules/host/code.md`）：`python3 script/framework.py milestone <sys> confirm --id M3 --confirm "<确认语句>"`。确认语句按固定模板生成——`确认 <sys> 签核放行（M3）通过`——主持者生成句子，开发者在自己的终端照抄执行；不问开发者用哪句，主持者不模拟终端。

## 里程碑审阅包

- **M1 方案确认**：只读**结论摘要**（主持者写进 `<sys>/milestone_notes/M1.md`，固定模板见下，闸门检查 3–6 条）+ 原文链接（信息总览、流程、方案三份产物的路径，不再整份内嵌）+ 全部方向/数值裁决 + 冲突与红线五问的处置 + 独立审查发现及处置 + 未决问题。
- **M2 规格冻结**：子系统规格书端口表；模块清单与类型；风险优先抽样 2–3 份模块规格书（结构 + 逻辑块）；测试要点总数与覆盖关系；审查发现处置表。抽样按"关联裁决数、审查发现数、回修次数、端口数"排序取前二，再按固定种子随机取一；包里的"抽样口径"一节写出排序结果与种子，同一子系统两次出包结果一致。
- 里程碑之后的变更：L0/L1 回修自动进行并进简报，列入下一个里程碑的回修清单；L2/L3 是决策。

### `milestone_notes/M1.md` 模板

三份产物各一段，每段 1–2 条，全文件 3–6 条；每条一句结论 + 依据出处（章节或裁决号），不要在摘要里重复正文：

```markdown
# M1 结论摘要（<sys>）

- 信息总览：<一句话结论>（依据：info_input/<sys>_info_overview.md §N）
- 信息总览：<冲突或红线五问的处置结论>（依据：同上 §M）
- 流程：<一句话结论>（依据：flow_doc/<sys>_flow.md §N）
- 方案：<一句话结论>（依据：plan_doc/<sys>_plan.md §N，或〔D0-001〕）
```

条数不足 3 条或超过 6 条时 `milestone confirm` 直接拒（摘要必须是唯一入口）。

## 审查要点（呈现与闸门）

下列要点是 `spec_review` 独立审查与主持者核对审阅包的清单；开发者只看里程碑审阅包，不逐项过。

- ①（行 3 方案）：待点选项逐条裁决；模块划分无孤儿无重叠；前后级无环；交互闭环；**共享资源三问必问**：大块存储归谁、可复用算子是否抽成共享模块、配置与状态归属；答不出列为待点选，不进入行 4
- ②（行 4 接口定义）：端口表列全且位宽依据可回溯；分批产出时按批呈现，下一批派发携带前批基线（章节口径、共用端口命名、位宽与时钟域假定）；跨批核对同名接口
- ③（行 5 结构生成）：连接表无悬空端口；直连命名合规；group 组内清单忠实继承行 3；新拆子模块清单置顶先审
- ④（行 6 逻辑块设计）：逻辑块与流程一致；复位与关键信号齐备；测试要点可验证；`spec_review` 发现逐条有处置，处置记入审查记录与小结

分批审核：停点 4 的模块规格书按 8–10 个一批，批间由主持者自行划分（派工分批属自动，不请开发者确认）；全部批次产出后做一次跨批一致性核对再送审。

- 呈现内容：产物路径、3–6 条结论、待点选项（大白话、涉及文档、情况说明）；出现即报、不攒批，并给出"推迟决定"一项（前置条件未达成的可先挂起），裁完再改。
- 呈现时用停点名字称呼（例："处理流程梳理"），首次出现写"行 2（处理流程梳理）"；只报编号开发者不知道在干什么，编号只留在命令与状态字段里。
- 跑 `tick` 前主持者独立跑 `python3 script/framework.py gate <sys> --stop N`，不采信自报数字；`tick` 的自动启动/送审/完成判据同样以闸门结果为准。
- 先查后问：把待点选项落盘前，先查输入文档、上游产物、已入库裁决与规则正文，漏查的退回角色自查。

## 派发与落盘

派发时携带：输入路径、停点号、必读规则路径（角色 `must_read`）。多个角色能并行的场合按 `rules/methodology.md` 的派工约束编排：先划文件归属，同一文件同一时间只有一个写入者；走查派给没参与该产物写作的子代理，作者与审查者派工号由主持者登记。角色返回后写入：

- `summary add`：本轮小结
- `problem <sys> add --stop N --kind ... --text "<问题一句话>"`：阻断或待裁决问题
- `handoff set`：写恢复入口（下一次会话先读这一条）

停点完成或里程碑通过后的 git 快照是自动的：主持者直接提交，提交历史就是审计轨迹，不再先把提交内容呈现给开发者确认。方向与数值由开发者点选；记录类裁决由智能体按 `rules/decision.md` 入库，全部条目进里程碑审阅包。
