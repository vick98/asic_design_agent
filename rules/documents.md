# 文档

文档按用途分三类，控制信息另算一类——它不是"写出来"的，是命令管出来的：

- **控制信息**：唯一事实源是子系统目录的 `state.json` 与 `events.jsonl`，只由引擎经 `script/framework.py` 命令写入；查询同样走命令（见下「控制信息与渲染物」）。
- **渲染物（派生物）**：`*_status.md`、`*_decision.md`、`*_brief.md`、里程碑审阅包与 `signoff/`——引擎随每次事务从控制信息重渲染，给人读、给 git diff。**不手改**（手改会在下一次事务被覆盖），agent 也不以读信息为目的打开它们。
- **产物**：信息总览、流程、方案、规格书。放在 `info_input/`、`flow_doc/`、`plan_doc/`、`spec_doc/`，由角色按章节模型写，只写设计本身。
- **工作底稿**：审查报告、转上游的反馈单、处置记录。放在 `report/`，只记发现与处置过程，不进闸门、不具效力。

控制信息随子系统走、读写都在命令里；产物由角色按章节模型写；工作底稿由主持者与审查角色写。不要混：产物里不写进度，控制信息不写设计正文，底稿里的发现处置完就进裁决表与问题清单、不留在底稿里当在办项。

## 产物的通用写法

- 正文从第 2 节起；标题和正文之间不插入进度表
- 正文不写"待裁决""自审""下一步"这类过程话，过程写进小结或控制文档
- 依裁决改过的地方用 `〔D0-001〕` 标记（点选入库即领正式号，没有临时号要替换）
- 章节名来自 `framework/templates/chapters.yaml`，列定义在 `rules/templates/`，不自行加章节
- 定义处写全（位宽、格式、推导出处一次写清）；引用处写一句结论，并指向本子系统里的章节
- 前向占位（如"公共单元实例名行 5 定"）在后续停点定名之后仍然为真：名字由模块规格书与裁决承载，不回填，也不为了补一个名字去改已完成停点的产物
- 后续裁决改掉的是已完成产物里已写死的数值或结构时，要回填该产物，并按指纹与级联退回该停点重推；这与前向占位是两回事，不要混用
- 编码时读模块规格书的端口表，不读子系统规格书里的模块摘要来代替端口表

## 控制信息与渲染物

控制信息的唯一事实源是 `state.json`（进度、问题、裁决、审查与运行记录）与 `events.jsonl`（留痕），只由引擎经命令写入；下面两份渲染物由引擎随每次事务重渲染。

**agent 怎么查（不许读文件代替）**：

- 裁决全量与过滤：`decision <sys> list [--json] [--kind 方向|数值|记录] [--stop N] [--stage S] [--grep <词|正则>] [--limit N]`；`--open` 只看未关闭的待裁决/已推迟问题
- 单条全档（含修订历史与关闭问题）：`decision <sys> list --id <D号>`
- 入库前比对正文：`decision <sys> similar --content "…"`（重合度排名；同一内容请走 `override`，不开新号）
- 问题清单：`problem <sys> list [--json] [--all] [--kind …] [--stop N] [--grep …]`；事项 `item <sys> list --json`；事件留痕 `events <sys> [--grep …] [--limit N] [--json]`
- 状态：`status <sys> --json`（机器可读）或 `status <sys>`（人读）
- `--json` 的口径与 `status --json` 一致：stdout 只有一份 JSON，错误走 stderr、退出码非 0

### `*_status.md`（渲染物）

引擎从 `state.json` 渲染的当前位置、流程状态、产出物台账、待解决问题、恢复入口与小结，给人读、给 git diff。进度只看状态枚举；agent 查状态用 `status <sys> --json`，不打开本文件。

### `*_decision.md`（渲染物）

引擎渲染的已入库裁决与待裁决问题视图，字段同 `decision list` 的输出：每条裁决含编号（`D<阶段>-<三位流水号>`）、类别（方向/数值/记录）、正文、来源（点选来自哪个问题与哪个选项，或 `mark:文件:行`）与入库时间；撤回的裁决保留在原编号下并标"已撤回"，不重新入库。agent 查裁决用 `decision list`（`--json`/`--grep`/`--id`），不打开本文件。

类别由提交者自报。三类入库与改动都是点选即入库，不要确认语句（见 `rules/decision.md`）；方向与数值类必须来自开发者点选并级联，记录类由智能体入库、不级联，疑似夹带实质变更的条目在里程碑审阅包里高亮。数值类裁决的正文只粘贴 `fx` 输出，不写手算数字。

### 工作底稿与审查报告（`report/`）

审查报告、转上游的反馈单、处置记录属工作底稿：放 `report/`，不进闸门（闸门只扫 `info_input/<sys>_info_overview.md`、`flow_doc/`、`plan_doc/`、`spec_doc/`），**不具效力**——效力只在裁决、输入文档强约束、权威、参考这四级里，底稿不在其中。

- 报告只报发现与建议，不改产物；发现同时用 `problem <sys> add --kind 阻断|待裁决 --stop N --text "..."` 登记到问题清单，在办状态以问题清单为准。
- 发现处置完毕、对应停点重新送完成后，报告即**归档**：不再作为在办清单，不再在恢复入口、小结与产物里被当作依据引用；此后追踪以 `decision <sys> list` 与 `problem <sys> list` 为准。
- 产物正文只引裁决号与章节，不引报告编号；报告编号只留在问题条目的 `source` 里作来源留痕。
- 归档时在报告开头写一行状态（归档时间、处置结论、在办依据指向何处），正文原样保留作历史，不追改。

## 路径与命名

| 内容 | 路径 |
|------|------|
| 输入总览 | `info_input/<sys>_info_overview.md` |
| 处理流程 | `flow_doc/<sys>_flow.md` |
| 系统方案 | `plan_doc/<sys>_plan.md` |
| 子系统规格书 | `spec_doc/<sys>_spec.md` |
| 模块规格书 | `spec_doc/<模块>_spec.md` |
| 中端签核 | `signoff/<sys>_signoff.md`（引擎渲染，不手改） |
| 问题与裁决 | 唯一事实源 `state.json`：写走 `decision`/`problem` 命令，查走 `decision list`/`problem list`（`--json`/`--grep`/`--id`）与 `decision similar` |

不手改 `state.json`、`events.jsonl` 与渲染物（`*_status.md`/`*_decision.md`/`*_brief.md`）；进度、问题、裁决都走命令，方向与数值裁决由开发者点选、记录类由智能体按 `rules/decision.md` 入库。agent 取控制信息一律走命令查询，不以读信息为目的打开这些文件。

## 常见错误

- 产物标题下面挂一张进度表，或者正文里写"下一步做什么"
- 用未入库的编号直接写进产物（应先入库换成 `D` 号）
- 同一数值在产物与控制文档里各写一套，还不标出处
- 引用别的规格书时只写"见规格书"，不写章节
- 把设计正文写进 `*_status.md`
- 以"查信息"为由打开 `state.json` 或渲染物——应走 `decision list`/`similar`、`problem list`、`status --json`、`events` 等命令查询
- 手改渲染物（`*_status.md`/`*_decision.md`）——下一次事务即被覆盖，改动丢失还污染 diff

## 交付前自检

1. 产物正文从第 2 节起，没有进度表与过程话
2. 依裁决改过的地方都带 `〔D…〕`（没有临时号，也没有别的占位写法）
3. 定义处写全，引用处有结论且指向章节
4. 渲染物与产物各归其位，`signoff/` 由引擎生成未手改
